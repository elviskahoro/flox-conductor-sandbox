## Post-run analysis (smoke run in Claude Code remote container — NOT the target sandbox class)

This first run happened in a Claude Code remote session (Ubuntu 24.04,
x86_64, egress via an allowlisting proxy), used purely to validate harness
mechanics before the real Conductor-sandbox run. Adjusted read of the table:

- **Stage 1 PASS (real):** the apt/deb bootstrap path works; flox installed
  in 47s and the deb's postinst brought up multi-user Nix cleanly.
- **Stage 2 PASS (real, and the headline):** the H1 environment — gtm-sdk's
  five catalog packages, flake pins removed — resolved, locked, and
  materialized atomically in **32s with no committed manifest.lock**, and all
  five tools verify under `.flox/run/.../bin`. Catalog fetches went to the
  Flox catalog/CDN and needed **no** GitHub egress.
- **Stage 3a/3b FAIL (environment-limited, not a harness defect):** both
  builds died before the build `command` ever ran, at flox's own build-tools
  bootstrap: `flox build` fetches `github:flox/nixpkgs/<pinned-rev>` as a
  tarball from `github.com/.../archive/<rev>.tar.gz`, and this session's
  proxy 403s GitHub `archive/` endpoints (release-asset downloads are
  allowed — the bd repackage curl itself would have succeeded). A Conductor
  sandbox with ordinary egress should not hit this; Stage 3 needs its real
  verdict from that run.
- **Stage 5 SKIP:** also unrunnable in this container for the same reason
  (the flake pin fetches `github:gastownhall/beads` via the archive
  endpoint).

### Genuine finding for gtm-sdk#445 either way

`flox build` has a hidden network dependency separate from the FloxHub
catalog: it must fetch `github:flox/nixpkgs` build tooling from GitHub, even
for a trivial `sandbox = "off"` build that itself needs no network. Any
machine that can `flox activate` catalog packages is NOT automatically a
machine that can `flox build`. This doesn't threaten the #445 plan (builds
are slated for a Mac/CI, which have open egress) but it does mean:
  1. the build/publish step can never quietly move onto a network-restricted
     sandbox as a fallback, and
  2. egress-restricted environments constrain WHERE the publish flow runs —
     worth stating explicitly in the AGENTS.md runbook the plan proposes.
