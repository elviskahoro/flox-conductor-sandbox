## Addendum — Stage 3b root-caused and fixed

The `tar: bd: Not found in archive` failure above is a real, reproducible bug, not host
flakiness (this is the same class of failure the `20260801-121814Z` row in
`findings/README.md` marked "never root-caused"). Fetching the release asset directly and
running `tar -tzf` on it shows every entry prefixed `./` (`./bd`, `./LICENSE`, ...). The build
command in `envs/repackage/.flox/env/manifest.toml` ran
`tar -xzf "${tmp}/${asset}" -C "${tmp}" bd`, filtering for a member literally named `bd`, which
never matches `./bd`. Fixed by extracting the whole archive
(`tar -xzf "${tmp}/${asset}" -C "${tmp}"`) and installing from `${tmp}/bd` as before. Verified
locally: `flox build --dir envs/repackage bd` now succeeds and
`./envs/repackage/result-bd/bin/bd --version` reports `bd version 1.1.2 (20e493e56)`.

Stage 4's PASS above remains **contaminated/non-authoritative**: this run's own `flox auth
status` output (Stage 4 body) shows the sandbox was already logged in as `elvis`, so it never
tested unauthenticated access — same caveat as the `20260801-201328Z` row in
`findings/README.md`. It does not change the standing H4 conclusion (SKIP is expected/private
catalog, resolved by issue #11).
